# Scene to Sound (S2S)
### Video Scene Analysis & Automated Background Music Generation

**동영상의 장면을 분석하고, 각 장면의 분위기에 어울리는 배경음악을 생성하여 자동으로 삽입하는 AI 기반 멀티미디어 시스템**

> Upload a video, analyze its scenes, generate context-aware background music, and automatically integrate the audio into the original video.

---

## 1. 프로젝트 소개 (Overview)

Scene to Sound(S2S)는 사용자가 업로드한 동영상을 분석하여 장면별 특성에 어울리는 배경음악을 자동으로 생성하고, 원본 영상에 삽입하는 웹 기반 멀티미디어 서비스입니다.
최근 reels, short와 같은 짧은 길이의 platform 인기와 수요가 급증하면서 영상 편집에 대한 편집시간을 줄이기 위한 부분에 초점을 맞췄습니다.

일반적인 영상 편집에서는 제작자가 직접 장면을 구분하고, 영상의 분위기에 맞는 음악을 검색하고, 구간별 음악을 편집해야 합니다. 이러한 과정은 반복적인 작업이 많고, 영상의 맥락에 적합한 음악을 선정하기 위해 별도의 시간과 노력이 필요합니다.

본 프로젝트에서는 이러한 작업을 자동화하기 위해 영상의 시각적 특징을 추출하는 CLIP 모델, 장면을 군집화하는 DBSCAN 알고리즘, 장면을 해석하여 음악 생성 프롬프트를 작성하는 Gemini API, 실제 오디오를 생성하는 Stable Audio Open을 연결했습니다.

사용자는 웹사이트에 동영상을 업로드하는 것만으로 장면 분석부터 음악 생성 및 영상 합성까지 이어지는 작업 흐름을 이용할 수 있도록 설계했습니다.

### 핵심 기능

- **자동 장면 분석:** CLIP 이미지 임베딩과 DBSCAN 군집화를 이용해 영상의 장면을 분석합니다.
- **장면별 시각적 맥락 파악:** 각 군집의 처음·중간·마지막 프레임을 추출하여 장면의 흐름을 요약합니다.
- **음악 생성 프롬프트 자동 작성:** Gemini API를 통해 장면별 분위기와 상황에 맞는 음악 생성 프롬프트를 생성합니다.
- **AI 기반 배경음악 생성:** Stable Audio Open을 활용하여 장면별 배경음악을 생성합니다.
- **음악 자동 삽입:** 생성된 오디오를 원본 영상의 장면 구간에 맞춰 배치하고 최종 영상을 구성합니다.
- **분산 서버 아키텍처:** CPU 기반 영상 분석 서버와 GPU 기반 음악 생성 서버를 분리하여 제한된 컴퓨팅 자원을 효율적으로 활용하도록 설계했습니다.

## 3. 시스템 아키텍처 (System Architecture)

본 시스템은 웹 인터페이스, CPU 기반 영상 분석 서버, GPU 기반 음악 생성 환경을 분리한 구조로 설계했습니다.

영상 분석과 음악 생성은 요구하는 컴퓨팅 자원이 다릅니다. CLIP 기반 프레임 임베딩과 군집화는 CPU 환경에서도 처리할 수 있지만, Stable Audio Open을 이용한 오디오 생성은 GPU 가속을 활용하는 것이 효율적입니다.

이에 따라 영상 분석은 Hugging Face Spaces에서, 음악 생성은 Google Colab의 GPU 환경에서 처리하도록 구성했습니다.

### 3.1. 웹 클라이언트 (React)

사용자가 직접 상호작용하는 웹 인터페이스입니다.

주요 역할은 다음과 같습니다.

- 사용자가 업로드한 동영상을 수신합니다.
- 서버에 전달할 영상 데이터를 전처리하고 요청 형식에 맞게 변환합니다.
- 영상 분석 서버에 요청을 전달합니다.
- 장면별 분석 결과와 음악 생성 결과를 전달받습니다.
- 생성된 음악을 해당 장면의 시간 구간에 맞춰 배치합니다.
- 최종 오디오와 원본 영상을 결합하여 결과물을 제공합니다.

영상 분석과 음악 생성을 브라우저 내부에서 모두 수행하지 않고 외부 서버에 위임하여 웹 클라이언트의 역할을 명확히 분리했습니다.

### 3.2. CPU 기반 영상 분석 서버 (Hugging Face Spaces)

영상 분석 서버는 Python 기반으로 구현했습니다.

동영상에서 프레임을 추출하고, CLIP 임베딩을 계산한 다음, DBSCAN을 이용해 장면을 군집화합니다. 이후 각 장면을 대표하는 프레임을 추출하여 Gemini API에 전달하고, 음악 생성에 사용할 프롬프트를 구성합니다.

음악 생성 모델을 이 서버에 함께 배치하지 않고 영상 분석과 프롬프트 생성에 집중하도록 구성했습니다.

이를 통해 상대적으로 가벼운 분석 작업과 GPU 자원이 필요한 생성 작업을 분리했습니다.

### 3.3. GPU 기반 음악 생성 서버 (Google Colab + ngrok)

Stable Audio Open의 오디오 생성은 Google Colab의 T4 GPU 환경을 활용하도록 구성했습니다.

Hugging Face 서버에서 생성한 장면별 프롬프트를 전달받아 오디오를 생성하고, 생성 결과를 웹 클라이언트가 이용할 수 있도록 반환합니다.

ngrok은 Colab 내부에서 실행되는 서버를 외부에서 접근할 수 있도록 연결하는 터널 역할을 합니다.

이 구조를 통해 별도의 상시 GPU 서버를 구축하지 않고도 GPU 가속을 이용한 음악 생성 파이프라인을 구현했습니다.

단, Colab 세션의 유지 시간, GPU 할당, ngrok 연결 상태에 영향을 받으므로 상용 서비스에서는 별도의 안정적인 추론 서버로 이전하는 것이 필요합니다.

## 4. 핵심 처리 파이프라인 (Core Pipeline)

### Step 1. 동영상 입력 및 전처리

사용자가 웹사이트에 동영상을 업로드하면 서버 분석에 적합한 형태로 전처리합니다.

영상은 시간에 따라 변화하는 시각 정보의 연속입니다. 모든 프레임을 동일한 방식으로 처리하면 계산량이 증가하므로, 영상에서 분석할 프레임을 추출하고 모델 입력 형식에 맞게 변환하는 과정이 필요합니다.

주요 처리 과정은 다음과 같습니다.

1. 사용자로부터 동영상 파일을 입력받습니다.
2. 서버 처리에 필요한 영상 데이터와 메타데이터를 준비합니다.
3. 시간 정보를 기준으로 분석할 프레임을 추출합니다.
4. 프레임을 CLIP 모델의 입력 규격에 맞게 전처리합니다.
5. 프레임별 임베딩 벡터를 생성합니다.

웹 전송 단계에서는 영상 데이터의 크기를 줄여 전달 부담을 완화하도록 설계했습니다. 이때 전송용 압축과 CLIP 입력용 이미지 전처리는 목적이 다릅니다. 전자는 네트워크 전송량을 줄이기 위한 것이고, 후자는 모델 입력 형식을 맞추기 위한 것입니다.

### Step 2. CLIP을 이용한 이미지 임베딩

**사용 모델: `openai/clip-vit-base-patch32`**

CLIP(Contrastive Language–Image Pre-training)은 이미지와 텍스트를 공통 임베딩 공간에 표현하도록 학습된 모델입니다.

본 프로젝트에서는 CLIP의 이미지 인코더를 이용하여 영상에서 추출한 프레임을 고정 길이의 벡터로 변환합니다.

이미지 자체를 DBSCAN에 직접 입력하는 것이 아니라, 이미지의 시각적 특징을 수치 벡터로 표현하여 군집화에 활용합니다.

#### 임베딩 처리 과정

```text
영상 프레임
    │
    ▼
이미지 전처리
    │
    ▼
CLIP Image Encoder
    │
    ▼
이미지 임베딩 벡터
    │
    ▼
프레임 간 시각적 유사도 분석
```

ViT-B/32 계열의 CLIP 모델은 프레임을 512차원 임베딩 공간에 표현할 수 있습니다.

이 벡터는 프레임의 시각적 특징을 수치적으로 비교할 수 있도록 해주며, 이후 DBSCAN을 통한 장면 군집화와 장면 대표 벡터 계산에 활용됩니다.

#### CLIP을 선택한 이유

첫째, 프레임의 시각적 특징을 고정 길이 벡터로 변환하여 다양한 장면을 동일한 데이터 구조로 비교할 수 있습니다.

둘째, 텍스트와 이미지가 연결된 임베딩 공간을 제공하므로 이후 장면의 분위기를 설명하는 텍스트 후보와 이미지 특징을 비교하는 데 활용할 수 있습니다.

셋째, 대규모 영상 분석 모델을 사용하지 않고 비교적 경량화된 모델을 활용하여 CPU 기반 분석 서버에서도 처리할 수 있는 구조를 목표로 했습니다.

특히 본 프로젝트에서는 단순히 영상에서 컷을 검출하는 것에 그치지 않고, 장면별 분위기 분석과 음악 생성까지 이어져야 했습니다. 이에 따라 후속 단계에서 재사용할 수 있는 시각적 특징 벡터를 생성하는 방식을 선택했습니다.

### Step 3. DBSCAN을 이용한 장면 군집화

**사용 알고리즘: DBSCAN (Density-Based Spatial Clustering of Applications with Noise)**

DBSCAN은 데이터가 밀집한 영역을 하나의 군집으로 묶고, 주변 데이터와 충분히 연결되지 않은 데이터를 노이즈로 분류하는 밀도 기반 군집화 알고리즘입니다.

K-means처럼 군집의 개수 \(K\)를 사전에 지정할 필요가 없다는 특징이 있습니다.

영상의 장면 개수는 동영상마다 다르므로, 군집 개수를 미리 지정하지 않고 프레임 간 특징의 밀도와 분포를 이용하는 접근이 적합하다고 판단했습니다.

#### DBSCAN의 핵심 개념

| 개념 | 설명 |
|---|---|
| `eps` | 두 데이터가 서로 이웃으로 인정받기 위한 최대 거리 |
| `min_samples` | 핵심 데이터로 인정받기 위해 주변에 필요한 최소 데이터 수 |
| Core Point | `eps` 이내에 최소 개수 이상의 데이터가 존재하는 핵심 데이터 |
| Border Point | 핵심 데이터 주변에 위치하지만 자체적으로 핵심 조건은 충족하지 않는 데이터 |
| Noise Point | 어느 군집에도 속하지 않는 데이터 |

#### 동작 원리

1. 각 프레임의 임베딩 벡터를 입력합니다.
2. 각 벡터를 기준으로 `eps` 이내에 존재하는 이웃 데이터를 탐색합니다.
3. 이웃 데이터 수가 `min_samples` 이상이면 핵심 데이터로 판단합니다.
4. 서로 밀도 연결된 데이터를 하나의 군집으로 확장합니다.
5. 군집에 연결되지 않는 데이터는 노이즈로 분류합니다.

이를 통해 시각적 특징이 비슷한 프레임들을 하나의 장면 그룹으로 묶는 방식으로 활용했습니다.

#### 영상 장면 분석에 DBSCAN을 적용한 이유

일반적인 영상은 장면 전환이 일정한 간격으로 발생하지 않습니다. 짧은 컷이 연속적으로 등장할 수도 있고, 하나의 장면이 비교적 길게 유지될 수도 있습니다.

DBSCAN은 군집 개수를 미리 지정할 필요가 없으며, 밀도 기반으로 군집을 구성할 수 있습니다. 또한 노이즈를 별도로 분류할 수 있어 다양한 영상에서 발생하는 프레임 분포에 대응할 수 있다는 장점이 있습니다.

다만 DBSCAN은 시간 순서를 직접 이해하는 알고리즘이 아닙니다. 이미지 임베딩 공간에서 가까운 프레임을 묶는 것이므로, 시간적으로 떨어진 유사 장면이 같은 군집에 들어갈 가능성이 있습니다.

따라서 실제 장면 분할 결과는 프레임 추출 방식, 시간 정보의 처리, 거리 척도, `eps` 및 `min_samples` 설정에 영향을 받습니다.

#### DBSCAN의 주요 하이퍼파라미터

| 파라미터 | 역할 | 조정 시 고려 사항 |
|---|---|---|
| `eps` | 이웃으로 인정할 최대 거리 | 값이 너무 작으면 군집이 과도하게 분리되고, 너무 크면 서로 다른 장면이 합쳐질 수 있음 |
| `min_samples` | 핵심 데이터의 최소 이웃 수 | 값이 너무 크면 많은 프레임이 노이즈로 분류될 수 있음 |
| 거리 척도 | 벡터 사이의 거리를 계산하는 방법 | 임베딩의 정규화 여부와 벡터 분포에 따라 결과가 달라질 수 있음 |

**중요:** 실제 코드에서 사용한 거리 척도와 벡터 정규화 방식에 맞춰 최종 README의 설정을 명시해야 합니다.

### Step 4. 컷 분할 데이터셋을 활용한 군집화 실험

군집화 알고리즘은 파라미터 설정에 따라 결과가 크게 달라질 수 있습니다. 따라서 기본 설정을 그대로 사용하는 대신, 장면 분할 데이터셋을 활용해 군집화 결과를 검토하고 하이퍼파라미터를 조정하는 실험을 진행했습니다.

이 과정의 목적은 단순히 군집을 생성하는 것이 아니라, 실제 영상의 장면 구분과 군집화 결과 사이의 차이를 줄이는 것입니다.

#### 실험 목적

- 서로 다른 장면이 하나의 군집으로 합쳐지는 경우를 확인합니다.
- 하나의 장면이 여러 군집으로 과도하게 분리되는 경우를 확인합니다.
- 노이즈로 분류되는 프레임의 비율을 확인합니다.
- 하이퍼파라미터 변화에 따라 군집 개수와 분할 결과가 어떻게 달라지는지 비교합니다.

#### 하이퍼파라미터 조정 항목

| 실험 항목 | 확인 목적 |
|---|---|
| `eps` 변화 | 군집의 연결 범위에 따른 장면 병합·분리 경향 확인 |
| `min_samples` 변화 | 군집 생성 조건과 노이즈 분류 경향 확인 |
| 프레임 추출 간격 | 프레임 밀도 변화가 군집화에 미치는 영향 확인 |
| 임베딩 벡터 처리 | 정규화 및 거리 계산 방식에 따른 결과 비교 |
| 실제 컷 경계와 비교 | 군집화 결과가 실제 장면 전환을 얼마나 반영하는지 확인 |

실험 결과는 군집 개수만으로 판단하지 않고, 실제 장면 경계와 비교하여 장면이 과도하게 합쳐지거나 분리되는 사례를 함께 검토하는 것이 중요합니다.

#### 실험 결과 기록

| 항목 | 기록할 내용 |
|---|---|
| 평가 데이터 | 사용한 컷 분할 데이터셋의 이름 및 버전 |
| `eps` | 실제 실험값 |
| `min_samples` | 실제 실험값 |
| 거리 척도 | 코드에 사용한 거리 계산 방식 |
| 군집 수 | 실험별 생성된 군집 개수 |
| 노이즈 비율 | 전체 프레임 중 노이즈로 분류된 비율 |
| 평가 지표 | 실제 사용한 분할 평가 지표 |
| 최종 설정 | 실제 코드에서 선택한 파라미터와 선정 근거 |

실제 실험 로그를 기준으로 위 표를 채우면, 알고리즘을 적용하는 데 그치지 않고 데이터 기반으로 모델 동작을 검토하고 개선했다는 점을 명확하게 설명할 수 있습니다.

### Step 5. 군집별 대표 프레임 추출

DBSCAN으로 장면 군집을 구성한 다음, 각 군집의 처음·중간·마지막에 해당하는 프레임을 추출합니다.

단일 프레임만 사용하면 특정 순간의 시각 정보에 지나치게 의존할 수 있습니다. 반면 장면의 서로 다른 시간 위치에서 프레임을 추출하면 장면의 시작과 전개, 종료에 해당하는 시각적 단서를 함께 활용할 수 있습니다.

#### 처리 흐름

```text
군집화된 장면
      │
      ├── 첫 번째 프레임
      │
      ├── 중간 프레임
      │
      └── 마지막 프레임
               │
               ▼
        대표 이미지 3장
               │
               ▼
         Gemini API 입력
```

대표 프레임 3장을 사용하면 전체 장면의 모든 프레임을 외부 API에 전달하지 않고도 장면의 주요 시각 정보를 전달할 수 있습니다.

이를 통해 API 입력을 제한하면서 장면별 음악 프롬프트를 생성하는 구조를 구현했습니다.

단, 세 프레임만으로 장면의 모든 행동이나 시간적 맥락을 완전히 이해할 수 있는 것은 아닙니다. 따라서 대표 프레임은 장면의 시각적 특성을 요약하기 위한 입력으로 활용합니다.

---

### Step 6. Gemini API를 이용한 음악 생성 프롬프트 작성

**사용 기술: Google Gemini API**

CLIP과 DBSCAN은 장면의 시각적 특징을 벡터화하고 군집화하는 역할을 담당합니다. 하지만 임베딩 벡터와 군집 번호만으로는 음악 생성 모델이 활용할 수 있는 구체적인 음악적 설명을 직접 얻기 어렵습니다.

이를 해결하기 위해 각 군집에서 추출한 대표 프레임 3장을 Gemini API에 전달하여 장면을 해석하고, 해당 장면에 어울리는 음악 생성 프롬프트를 작성하도록 구성했습니다.

#### 처리 과정

1. 군집별 처음·중간·마지막 프레임을 준비합니다.
2. 대표 프레임 3장을 Gemini API에 전달합니다.
3. 장면의 시각적 맥락과 분위기를 파악합니다.
4. 장면에 어울리는 음악의 분위기, 장르, 악기, 리듬 등의 표현을 포함한 프롬프트를 생성합니다.
5. 생성된 프롬프트를 Stable Audio Open의 입력으로 전달합니다.

#### 프롬프트 생성의 역할

Gemini API는 실제 오디오를 생성하는 모델이 아니라, 음악 생성 모델에 전달할 텍스트를 작성하는 역할을 담당합니다.

예를 들어 장면이 평화로운 자연 풍경이라면 잔잔한 분위기와 부드러운 악기 구성을 강조할 수 있고, 빠르게 움직이는 장면이라면 역동적인 리듬과 에너지감을 강조할 수 있습니다.

이처럼 장면을 설명하는 시각적 정보와 음악의 특징을 연결하여, 단순한 배경음악 생성보다 장면 맥락에 맞는 음악 생성을 목표로 했습니다.

---

### Step 7. Stable Audio Open을 이용한 음악 생성

**사용 모델: Stable Audio Open**

Stable Audio Open은 텍스트 프롬프트를 기반으로 오디오를 생성하는 모델입니다.

본 프로젝트에서는 Gemini API가 생성한 장면별 음악 프롬프트를 입력으로 사용하여 배경음악을 생성했습니다.

#### 처리 과정

```text
장면별 대표 프레임
         │
         ▼
     Gemini API
         │
         ▼
음악 생성 프롬프트
         │
         ▼
  Stable Audio Open
         │
         ▼
   생성된 오디오 파일
```

영상 분석 서버가 장면별 프롬프트를 생성하면, GPU 환경에서 Stable Audio Open을 이용해 해당 프롬프트에 대응하는 오디오를 생성합니다.

GPU를 활용하면 모델 추론 시간을 단축할 수 있으며, 본 프로젝트에서는 Google Colab의 T4 GPU 환경을 이용해 약 2분 분량의 오디오를 약 20초 수준에 생성하는 실험 결과를 확인했습니다.

해당 시간은 당시 사용한 환경과 생성 설정에서 관찰한 값이며, 입력 길이, 추론 설정, GPU 할당 상태 등에 따라 달라질 수 있습니다.

#### 장면별 음악 생성

음악을 영상 전체에 하나만 생성하는 대신, 장면별 프롬프트를 이용해 각각의 장면에 대응하는 오디오를 생성하도록 구성했습니다.

이렇게 하면 영상의 분위기가 달라지는 구간에서 음악도 달라질 수 있어, 장면별 맥락을 반영한 배경음악 구성을 목표로 할 수 있습니다.

---

### Step 8. 장면별 오디오 배치 및 영상 합성

음악 생성이 완료되면 각 오디오를 해당 장면의 시간 구간과 연결하고, 원본 영상에 삽입하여 최종 결과물을 구성합니다.

#### 주요 처리 과정

1. 장면별 시작 시간과 종료 시간을 확인합니다.
2. 각 장면에 대응하는 생성 오디오를 연결합니다.
3. 장면 전환 구간에 맞춰 오디오를 배치합니다.
4. 필요에 따라 페이드 인·페이드 아웃 및 크로스페이드를 적용합니다.
5. 음성 구간과 배경음악의 관계를 고려하여 최종 오디오를 구성합니다.
6. 원본 영상과 오디오를 결합하여 최종 결과물을 생성합니다.

장면별 음악을 단순히 이어 붙이면 장면이 바뀔 때 음량이나 음악의 분위기가 갑자기 변할 수 있습니다. 페이드 인·아웃과 크로스페이드는 이러한 전환을 완화하는 데 활용할 수 있습니다.

또한 Silero VAD(Voice Activity Detection)를 활용하여 음성이 존재하는 구간을 감지하고, 배경음악을 음성과 함께 재생할 때의 구간별 음량 처리를 고려했습니다.

VAD는 음성 구간을 판별하는 기술이며, 음성의 실제 크기나 음악의 적절한 음량을 직접 판단하는 것과는 다릅니다. 따라서 음성 구간 감지와 음악의 감쇠·믹싱은 별개의 처리 단계로 구분해야 합니다.

최종 합성 단계에서는 영상의 시간 정보와 생성 오디오의 길이를 일치시키는 것이 중요합니다. 음악 생성 결과가 장면 길이보다 길거나 짧은 경우, 실제 구현된 자르기·배치·페이드 처리 방식에 따라 결과가 달라질 수 있습니다.

## 5. 음악 프롬프트 및 장면 분위기 매칭 실험

본 프로젝트에서는 영상의 시각적 특징을 음악 생성 프롬프트로 연결하는 과정에서도 실험을 진행했습니다.

CLIP 이미지 임베딩을 이용하면 영상 프레임과 텍스트 후보를 동일한 임베딩 공간에서 비교할 수 있습니다. 이를 활용해 미리 정의한 분위기·장르 설명문 후보와 영상의 시각적 특징 사이의 유사도를 계산하는 방식을 검토했습니다.

### 5.1. PCA와 Cosine Similarity

**PCA (Principal Component Analysis)**

PCA는 데이터의 분산을 설명하는 주요 방향을 찾아 고차원 데이터를 더 낮은 차원의 표현으로 변환하는 차원 축소 기법입니다.

본 프로젝트에서는 군집별 대표 벡터를 구성하고 활용하는 과정에서 PCA를 이용하는 방식을 적용했습니다.

**Cosine Similarity**

Cosine Similarity는 두 벡터의 방향이 얼마나 유사한지를 측정하는 방법입니다.

\[
\operatorname{CosSim}(A,B)
=
\frac{A\cdot B}{\|A\|\|B\|}
\]

CLIP 임베딩 공간에서는 이미지 벡터와 텍스트 벡터 사이의 코사인 유사도를 계산하여, 영상의 시각적 특징과 분위기 설명문 후보가 얼마나 유사한지 비교할 수 있습니다.

일반적으로 유사도가 높을수록 두 임베딩의 방향이 비슷하다는 뜻입니다. 다만 유사도 값이 높다는 사실만으로 실제 음악의 품질이나 장면 적합성이 보장되는 것은 아닙니다.

### 5.2. 텍스트 후보 구성 방식 비교

분위기 및 장르를 표현하는 텍스트 후보의 구성 방식에 따라 이미지와 텍스트 간 유사도 결과가 달라질 수 있습니다.

프로젝트 실험에서는 짧은 라벨 형태의 텍스트 후보와 설명문 형태의 후보를 비교했습니다.

| 후보 구성 방식 | 관찰된 결과 |
|---|---:|
| 짧은 라벨 기반 후보 | 평균 유사도 0.8683 |
| 문장형 설명 후보 | 평균 유사도 0.5523 |

위 수치는 실험 당시 사용한 후보 집합과 평가 방식에서 관찰한 값입니다. 두 수치만으로 분류 정확도나 음악 적합도를 직접 의미한다고 해석할 수는 없습니다. 서로 다른 후보 구성 방식의 결과를 비교할 때에는 동일한 평가 데이터와 동일한 계산 절차를 적용하는 것이 중요합니다.

실험을 통해 텍스트의 표현 방식이 이미지·텍스트 임베딩 유사도에 영향을 줄 수 있음을 확인하고, 후보 문구의 구성과 비교 방식을 검토했습니다.

### 5.3. 후보 임베딩 재사용

분위기 및 장르 후보를 사전에 정의할 수 있는 경우, 매 프레임마다 동일한 텍스트를 다시 인코딩할 필요가 없습니다.

따라서 텍스트 후보의 임베딩을 미리 계산해 Lookup Table 형태로 보관하고, 영상에서 추출한 이미지 벡터와 비교하는 방식을 활용할 수 있습니다.

이 접근은 반복적인 텍스트 인코딩을 줄이고, 고정된 후보 집합을 사용하는 상황에서 처리 효율을 높이는 데 도움이 됩니다.

또한 이미 계산한 프레임 임베딩을 후속 단계에서 재사용하면 동일한 프레임에 대한 중복 계산을 줄일 수 있습니다.

**구현 구분:** PCA 기반 대표 벡터, 코사인 유사도 기반 후보 매칭, Lookup Table을 이용한 임베딩 재사용은 각각 다른 역할을 담당합니다. 실제 실행 파이프라인에서 적용한 단계와 실험 단계에서 검토한 방법을 구분하여 기술하는 것이 중요합니다.

## 6. 핵심 알고리즘 선정 이유

| 기술 | 주요 역할 | 선정 이유 |
|---|---|---|
| CLIP | 프레임의 시각적 특징을 임베딩으로 변환 | 이미지와 텍스트를 연결하는 표현 공간을 제공 |
| DBSCAN | 유사한 프레임을 군집화 | 군집 수를 사전에 지정하지 않고 밀도 기반으로 그룹 구성 |
| PCA | 벡터의 주요 특징을 저차원으로 표현 | 군집 대표 표현 및 벡터 분석에 활용 |
| Cosine Similarity | 이미지·텍스트 임베딩 간 유사도 계산 | 분위기 및 장르 설명문 후보 비교 |
| Gemini API | 장면별 음악 생성 프롬프트 작성 | 대표 프레임의 시각적 맥락을 자연어로 변환 |
| Stable Audio Open | 텍스트 조건 기반 오디오 생성 | 장면별 음악 생성 |
| Silero VAD | 음성 구간 감지 | 음성과 배경음악의 구간별 처리를 위한 정보 제공 |

각 기술은 독립적으로 작동하는 것이 아니라, 영상에서 추출한 시각적 특징을 자연어 기반 음악 생성 조건으로 변환하고, 생성된 오디오를 다시 영상의 시간 정보에 연결하는 하나의 파이프라인을 구성합니다.

## 7. 기술적 의사결정 및 문제 해결

### 7.1. 영상 분석과 음악 생성의 서버 분리

**문제**

영상 분석과 음악 생성은 서로 다른 연산 자원을 요구합니다. 특히 음악 생성 모델을 CPU 기반 서버에서 실행하면 처리 시간이 증가할 수 있으며, GPU 환경을 모든 작업에 사용하면 자원 활용 측면에서 비효율이 발생할 수 있습니다.

**접근 방식**

- CLIP 기반 프레임 분석과 군집화는 CPU 기반 서버에서 수행합니다.
- Gemini API를 이용한 프롬프트 생성은 영상 분석 단계와 연결합니다.
- Stable Audio Open의 추론은 GPU 기반 환경에서 수행합니다.
- 서버 간에는 장면 구간과 음악 생성 프롬프트, 오디오 결과를 전달합니다.

**의의**

작업의 연산 특성에 따라 실행 환경을 분리하여, 제한된 자원에서도 영상 분석부터 음악 생성까지 이어지는 전체 시스템을 구성했습니다.

### 7.2. 모델 크기와 실행 효율 고려

영상 분석에 활용할 모델을 선정할 때에는 분석 성능뿐 아니라 모델 크기와 CPU 환경에서의 실행 가능성도 고려해야 합니다.

본 프로젝트에서는 대규모 영상 모델을 무조건 사용하는 대신, CLIP의 이미지 임베딩을 이용해 장면의 시각적 특징을 추출하고 군집화하는 접근을 사용했습니다.

또한 장면별 대표 프레임을 세 장으로 제한하여 Gemini API에 전달함으로써, 전체 프레임을 모두 전송하는 방식보다 입력 규모를 관리하기 쉽도록 구성했습니다.

### 7.3. 장면 분할과 음악 생성의 연결

장면 분할이 정확하지 않으면 음악 생성 단계의 결과도 영향을 받습니다. 서로 다른 장면이 하나의 군집에 포함되면 하나의 프롬프트가 여러 분위기를 대표해야 할 수 있고, 하나의 장면이 지나치게 분리되면 불필요한 음악 생성 작업이 늘어날 수 있습니다.

따라서 장면 분할은 단순한 전처리가 아니라, 후속 음악 생성의 맥락과 처리량에 영향을 주는 핵심 단계입니다.

이를 고려하여 컷 분할 데이터셋을 이용한 군집화 실험과 하이퍼파라미터 검토를 진행했습니다.

### 7.4. 외부 서버 연결 및 결과 전달

Hugging Face 서버와 Google Colab의 음악 생성 환경을 연결할 때에는 분석 결과가 올바른 장면과 대응하는지, 요청한 프롬프트에 대한 오디오가 정상적으로 반환되는지 확인해야 합니다.

또한 외부 GPU 세션은 연결이 끊기거나 실행 환경이 초기화될 수 있습니다. 이러한 환경적 제약을 고려하여 영상 분석과 음악 생성을 분리하고, 각 단계의 입력과 출력을 명확히 구분하는 구조를 채택했습니다.

## 10. 한계점 및 향후 개선 방향

### 장면 분할 정확도 개선

DBSCAN은 시각적 특징의 밀도를 이용하므로 시간적 순서나 실제 컷 전환을 직접 이해하지 않습니다. 향후에는 실제 장면 경계 평가와 시간 정보 활용을 강화하여 과도한 병합과 분리를 줄일 수 있습니다.

### 프롬프트 품질 및 일관성 개선

대표 프레임 세 장은 장면의 전체 맥락을 완벽하게 설명하지 못할 수 있습니다. 프롬프트 형식을 표준화하고 장면 설명의 일관성을 검증하면 음악 생성 결과의 변동을 줄이는 데 도움이 될 수 있습니다.

### 오디오 전환 품질 개선

장면별로 생성된 음악을 연결하면 장면 전환 시 음량과 분위기가 갑자기 바뀔 수 있습니다. 크로스페이드, 음량 정규화, 장면 간 음악적 일관성 평가 등을 통해 전환 품질을 개선할 수 있습니다.

### 음성과 배경음악의 균형

VAD로 음성 구간을 감지하는 것만으로 최적의 음악 음량을 결정할 수는 없습니다. 향후 음성의 실제 음량을 고려한 자동 덕킹(ducking), 구간별 음량 조절, 믹싱 품질 평가를 추가할 수 있습니다.

### 서비스 운영 안정성

Google Colab과 ngrok을 이용한 구성은 프로토타입 개발에 유용하지만, 세션 유지 시간과 외부 연결 상태에 영향을 받습니다. 상용 서비스로 확장하려면 안정적인 GPU 추론 서버, 요청 큐, 작업 상태 관리, 오류 복구 및 결과 파일 저장 정책을 별도로 설계할 필요가 있습니다.

## 11. 프로젝트 요약 (Summary)

Scene to Sound는 영상 분석 모델과 생성형 AI를 개별적으로 사용하는 데 그치지 않고, 영상의 시각적 특징을 추출하고 장면을 군집화한 다음, 장면별 음악 프롬프트 생성과 오디오 생성, 최종 영상 합성까지 연결한 멀티미디어 시스템입니다.

CLIP 임베딩과 DBSCAN을 이용한 장면 분석, Gemini API를 통한 음악 생성 프롬프트 작성, Stable Audio Open 기반 오디오 생성, React 웹 인터페이스 및 분산 서버 구조를 결합했습니다.

특히 제한된 CPU·GPU 자원과 외부 API 환경을 고려하여 시스템의 각 단계를 분리하고 연결함으로써, 컴퓨터 비전 알고리즘을 실제 사용자 서비스의 기능으로 통합하는 경험을 쌓았습니다.
